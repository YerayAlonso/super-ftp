# Signed update work in progress

This is not yet a release procedure. Do not publish an updater-enabled build until end-to-end tests, the release process and the threat model have been reviewed.

The desktop client checks the public GitHub releases API for announcements. A separate Tauri updater check uses a fixed HTTPS manifest URL for the stable or preview channel. The planned manifests are `updates/stable.json` and `updates/preview.json` on the repository's default branch; neither exists yet. An absent manifest must not offer an install. The updater accepts only installer URLs under this repository's GitHub release downloads and verifies the installer against the embedded public key before execution. Updating on Windows closes the application, so active or queued transfers block installation; the queue lock also blocks new transfers during the final check and install.

Each manifest must contain a version and the exact installer URL and `.sig` content generated for that version. Signatures and manifests must be generated and independently verified against the exact release artifact before publishing. A GitHub release is not automatically an updater release: its signed manifest must also be published on the selected channel. Prereleases must never enter the stable channel. The first build with this feature must be installed manually; older builds do not contain the updater public key.

After signing an installer with `tauri signer sign --app-version VERSION`, a local manifest can be generated with `node scripts/create-update-manifest.mjs VERSION INSTALLER SIGNATURE OUTPUT`. The output must not already exist. The generator checks formatting and the version in the signature's comment but **does not authenticate** either the signature or the installer; verification using the actual updater remains mandatory. Publish the resulting manifest only after the matching release asset has been uploaded and tested.

The signing private key and its password must remain outside the repository and release assets. Losing the key prevents signed updates for installations that trust it; key rotation and incident response must be designed before launch. Tauri updater signatures are distinct from Windows Authenticode signing; they do not eliminate Windows warnings for unsigned installers.

Remaining before launch: produce an actual signed test release and manifests, test valid and altered signatures and modified artifacts, exercise the installer and upgrade in a clean Windows environment, review downloads, redirects and resource limits, test transfer races and failure recovery, document the signing and publishing workflow, audit new dependencies and refresh third-party notices. Automatic startup checks contact GitHub without credentials and disclose network metadata such as IP address.

Local verification performed: a disposable signing key was used to exercise manifest generation; a separate local installer fixture was signed by the maintainer with the project key and verified using the configured public key. The updater verifier rejected modified bytes and a mismatched announced version. This did not test a network download, launch an installer, or prove that a published manifest and artifact match. Windows Rust and UI tests are separate from a full upgrade test.

The `Signed Windows upgrade test` workflow has also exercised a loopback HTTP fixture, the shared bounded-download and signature verification code, and a real NSIS upgrade from 0.1.2 to a 0.1.3 test installer on an isolated runner using an ephemeral key. It checked the installed executable against the test installer. This does not exercise production HTTPS redirect handling, public manifests, the actual project signing key, the UI, or concurrent active transfers; those still require verification.
